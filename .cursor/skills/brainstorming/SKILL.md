# 业务方案探索（Brainstorming）

方法源自 [obra/superpowers](https://github.com/obra/superpowers) 的 brainstorming skill，
按本仓库约定改写。核心规则**原样保留**：

> **用户批准之前，不得进入实现。**

这道闸门是三段式节奏的分界线（见 skill `implementation-autonomy` §0）：
闸门之前**频繁对**，闸门之后**不打断**。闸门本身不许拆。

## 0. 先分档

不同规模用不同深度。**判错档比谈得不够更糟**——小改动走全流程是浪费，
大改动走捷径是埋雷。

| 档 | 什么时候 | 产出 |
|---|---|---|
| **探路（Spike）** | 「这事能不能做 / 现状是什么样」 | 2-3 句说清要查什么 → 查 → 给结论和建议 |
| **有界（Bounded）** | 已有代码上的确定范围改动 | 问关键澄清问题 → **在对话里**给简短方案 → 停 |
| **架构级（Architectural）** | 新模块、跨模块、改数据模型、改核心流程 | 完整流程（§2） |

拿不准就问用户属于哪一档，别默认往低了走。

本仓库的额外信号——命中任一，**至少**按架构级：
- 动 `dw_*` / `sys_*` 表结构或 `deploy/init-scripts/`
- 动 Function Unit 的设计产物、导入导出、版本回滚
- 动分派链（BPMN / assignee / BU-Role）
- 同一改动要三端（portal / admin / dw）同步

## 1. 探路与有界

**探路**：先说清「我要查什么、为什么这么查」，得到认可再查。查完给**结论 + 建议**，
不是给一堆文件路径。

**有界**：
1. 问真正影响做法的澄清问题（不要为了显得严谨而凑问题）
2. 在对话里给方案：改哪里、怎么改、有什么取舍。几句话到几段
3. **停下来等拍板**

## 2. 架构级完整流程

### 2.1 先读，再问

按 `reasoning-protocol` Phase 1：读目标文件和直接依赖，Grep 确认相关符号真实存在，
评估爆炸半径。**不要基于文件名猜测现状**。

读完之后问的问题才有价值——否则会问出一堆读代码就能回答的问题。

### 2.2 问澄清问题

只问**答案会改变做法**的问题。典型有价值的：

- 业务语义边界：「A 和 B 在业务上是不是同一类东西？」
- 谁是权威：「这个值以设计器配置为准还是以运行时数据为准？」
- 存量怎么办：「已有的 FU / 已保存的数据要不要兼容？」
- 范围：「这次要不要覆盖 X？」

一次问一组，别一口气抛十个。

### 2.3 提 2-3 个方案 —— 这是本档的核心

**不是给一个方案问「行不行」，是给几个真实不同的方案让用户选。**

每个方案写清：

| 维度 | 内容 |
|---|---|
| 做法 | 一句话说清它的本质区别 |
| 改动范围 | 碰哪些模块/文件，大概多大 |
| 取舍 | 它好在哪、代价是什么 |
| 风险 | 最坏会怎样、存量数据会不会受影响 |

要求：

- **方案之间必须是真的不同路**，不是同一条路的三种参数。凑数的方案比不凑更坏
- 只有一条路可走时，**说明白为什么另外的路不通**，而不是假装有选择
- 给推荐，并说清推荐理由。不要把选择权当包袱全丢回去

### 2.4 分节确认

方案选定后，按节走：数据模型 → 判据/业务规则 → 影响链 → 边界与存量兼容。
**每节讲完停一下**，确认了再进下一节。

一口气把所有细节讲完，用户只能全盘接受或全盘推翻，没法在中途纠偏——
而中途纠偏正是这个阶段最值钱的东西。

### 2.5 落成 Plan

方案对齐后写 Plan（用 skill `feature-design-plan` / `/plan`）：范围、选型、
爆炸半径、验收、验证、分期。

自己先审一遍 Plan 再交——尤其检查：有没有写进没验证过的符号、有没有偷偷扩大范围。

## 3. 硬性边界

- ❌ 用户批准之前**不写产品代码**。读代码、跑只读查询、写探针验证判据可以
- ❌ 不要「先写一版看看」——这等于绕过闸门
- ✅ 用户明说「直接做」→ 记下这是用户的决定，跳到实现
- ✅ 方案期发现需求本身有矛盾 → 当场提出来，这正是这个阶段该干的

## 4. 交接

用户拍板 **业务方案** 后，进入 skill `implementation-autonomy`：
先讲 **技术方案**（改哪些文件 / 技术决策 / 影响链 / 通用性 / 验证方式 / 不做什么），
再拍一次板，然后实现期不打断。

**两次拍板不是重复**：这里定「做什么」，那里定「怎么做」。

## 5. 自检清单

- [ ] 分档判断做过，拿不准问过用户
- [ ] 读过代码再问问题，没问「读一下就知道」的问题
- [ ] 架构级给了 2-3 个**真的不同**的方案，不是一个方案问行不行
- [ ] 每个方案写了改动范围、取舍、风险
- [ ] 给了推荐和推荐理由
- [ ] 分节确认，没有一口气讲完所有细节
- [ ] 批准之前没有写任何产品代码
- [ ] Plan 里没有未验证的符号名，范围没有偷偷扩大
