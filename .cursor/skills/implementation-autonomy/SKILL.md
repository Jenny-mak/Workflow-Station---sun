# 实现期自主（Implementation Autonomy）

本 skill 管**两道闸门之间**的那一段：业务方案已定 → 技术方案对齐 → 实现 → 交付。

- 业务方案怎么定（做什么）→ 不在本文范围
- 提交/合并前怎么审 → `code-review`
- 报「已修复」前的证据门 → `bugfix-verification`

## 0. 三段式节奏

| 阶段 | 交互密度 | 谁拍板 |
|---|---|---|
| ① 业务方案 | **频繁对话**、开放探索、多个方案比选 | 用户 |
| ② 技术方案 | **一次性讲全**，用户可驳回重来 | 用户 |
| ③ 实现 | **不打断** | 我 |

②拍板那一刻 = 实现授权。之后除非**方案本身被证伪**（§3），否则做完再说话。

> 「不要每一步都来问我」和「业务讨论要频繁对」不矛盾：
> 前者管 ③，后者管 ①②。把问题**前移到方案期**，而不是消灭问题。

## 1. 技术方案要讲哪几项

②阶段一次性给全，缺项等于没对齐。每项都要具体到可反驳：

| 项 | 要求 | 反例 |
|---|---|---|
| **改哪些文件** | 具体路径 + 每个文件改什么 | ❌「相关模块」「几个组件」 |
| **关键技术决策** | 判据从哪读（配置/元数据/稳定 code）、为什么不用另一种 | ❌「按现有方式处理」 |
| **影响链** | 接口↔实现↔调用方；Entity→SQL→DTO→前端；i18n 三语；配置→Docker/K8s | ❌ 只说主路径 |
| **通用性** | 怎么保证不硬编码 FU/表/字段；新建 FU 与已有 FU 都成立 | ❌「会注意通用性」 |
| **验证方式** | 跑什么命令、要不要截图、要不要双样本/多主体 | ❌「会测试」 |
| **不做什么** | 明确划在范围外的 | ❌ 不写（默认全做 = 范围蔓延） |

这几项对着 `code-review` 的门禁列（§3 影响链 / §4 通用性双样本 / §9 放行条件）。
**②讲清楚 = ④ review 不返工。**

先决条件按 `reasoning-protocol` Phase 1-2 做完（读上下文、Grep 验证符号真实存在、评估爆炸半径、
选最小变更路径），不要在方案里写没验证过的符号名。

## 2. 拍板后：实现期不打断

### 自己定的（不要问）

- 命名、文件组织、函数拆分
- 用哪个既有工具/composable（按 `code-quality-standards` §1 复用优先）
- 测试怎么写、写几个
- 方案内的所有技术细节

### 不清楚 → 去查，不是来问

**「不清楚的地方不要做」的正确执行是先查清楚，不是先问人。**

| 不清楚什么 | 怎么查 |
|---|---|
| 某个配置/字段存不存在 | 查库 `\d <表>` + Grep 后端 DTO + Grep 前端类型 |
| 某个方法签名 | Grep 确认（`ai-guardrails` 幽灵 API） |
| 现有代码为什么这么写 | `git log -S` / 读测试 / 读同模块同类实现 |
| 判据该读哪个配置 | `config-over-heuristics` §1 |
| 行为对不对 | 写个测试跑一下 |

查完仍无解 → 才是 §3 的中断条件。

## 3. 什么时候必须回头找用户

**只有一类：方案被证伪。** 判据直接引用 `code-review` §8 的 Blocker 定义：

- 实现中发现 ②的方案**有洞**（技术上走不通、或会造成数据损坏/越权/破坏性不兼容）
- 碰到 ②**没覆盖的业务分叉**（两种做法业务语义不同，我无权替用户选）
- 发现真实凭证/PII（立即停，`code-review` §5）
- 需要改 ②明确划在范围外的东西

中断时给：**问题 + 为什么方案走不通 + 2-3 个可选方向 + 我的推荐**。不要只抛问题。

### 不构成中断理由

- 技术难 / 要多读几个文件 / 要多写几个测试
- 发现存量代码不好看（按 `error-handling-governance` 红线 4：改别人代码前先给出反例；
  没反例就记进「范围外问题」，别顺手改）
- 想确认「这样做对吗」——方案已拍板，做完用 `code-review` 验

## 4. 最少代码（Simplicity First）

> **最少代码解决被要求的问题。不写投机性代码。**

每一行改动都要能追溯到用户的需求。三条禁令：

### 4.1 不写没被要求的功能

没要求的配置项、没要求的开关、没要求的扩展点、"顺便加的" —— 全部不写。
需求边界之外的想法记进「范围外问题」，让用户决定。

### 4.2 不做过早抽象

`ai-guardrails` 已定：不加"以防将来需要"的抽象层、不把 if-else 重构成策略模式、
不在只有一个实现的地方抽接口。

**补充判据**：抽象的正当理由是**当下就有 ≥2 个真实调用点**，不是"将来可能有"。
`code-quality-standards` 要求「同一逻辑 ≥2 个服务出现即提取」——注意是**已经出现**，不是预判会出现。

### 4.3 不加防御性兜底 —— 有错误就报出来

**这条完全按 `error-handling-governance`（`alwaysApply`，红线 1-2）执行，本文不复述。**

要点：默认抛出/向上传播；`catch` 只 log 不 rethrow、`?? 默认值`、`|| []`、`.orElse(null)`、
`if (!x) return 旧逻辑` 一律视为 bug；豁免只有三类，判据是**「降级后是功能变少还是数据变错」**，
且必须写 `// FALLBACK(external|migration|ux): <依据>`。

> ⚠️ 与 `reasoning-protocol` Phase 3 第 10 条「防御性编程：不信任任何外部输入」的边界：
> **校验外部输入 = 该做**（在边界处验，不合法就**抛**）；
> **吞掉内部异常/给缺失值编造默认值 = 禁止**。
> 两者的区别是「拒绝坏数据」vs「假装数据没坏」。

### 4.4 外科式改动

只碰必须碰的。只清理**自己这次改动造成**的死代码（变成未使用的 import、变成死参数的入参），
**不要删预先存在的死代码**——那是独立的一次改动，记进「范围外问题」。

## 5. 自检清单

**②对齐前**
- [ ] 六项讲全（改哪些文件 / 技术决策 / 影响链 / 通用性 / 验证方式 / 不做什么）
- [ ] 方案里引用的每个类名、方法名、字段名都 Grep 验证过真实存在
- [ ] 爆炸半径评估过，跨模块的说明了

**③实现中**
- [ ] 不清楚的先查（库/Grep/测试），查完无解才中断
- [ ] 中断只因方案被证伪，且给了 2-3 个方向 + 推荐
- [ ] 没有顺手改范围外的代码

**交付前**
- [ ] 每一行改动都能追溯到需求（逐文件问「删掉它验收还过吗」）
- [ ] 没有投机性代码 / 过早抽象 / 单实现接口
- [ ] 没有新增静默兜底；确需降级的写了 `// FALLBACK(...)` 标签和依据
- [ ] 只清理了自己造成的死代码
- [ ] 范围外发现的问题已记录，而不是顺手改掉

## 6. 与其他规则/skill 的关系

| 关注点 | 去哪 |
|---|---|
| 兜底与错误处理（红线全文） | `error-handling-governance`（alwaysApply） |
| 过度工程化、幽灵 API、风格漂移 | `ai-guardrails`（alwaysApply） |
| 长度/复用/分层/API 标准 | `code-quality-standards`（alwaysApply） |
| 按变更类型选工作流 | `change-playbook`（alwaysApply） |
| 写代码前的结构化推理 | `reasoning-protocol`（alwaysApply） |
| 判据靠名字猜 → 改成读配置 | skill `config-over-heuristics` |
| 报「已修复」前的证据门 | skill `bugfix-verification` |
| 提交/合并前审查 | skill `code-review` |
| 功能/模块设计 Plan | skill `feature-design-plan`（`/plan`） |
